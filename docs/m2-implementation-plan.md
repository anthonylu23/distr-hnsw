# M2 implementation plan

The milestone scope and acceptance gate are in [roadmap.md](roadmap.md) (M2);
the design is DESIGN §3 (Tailscale integration), §9 (authentication and
authorization), and §10 (key custody). This page records how M2 is built,
in what order, and how each criterion will be proven.

## Starting point

- Agents bind to loopback only and accept any local request, including
  `DELETE` and inventory (`crates/distr-hnsw/src/agent.rs`).
- The portal is a set of one-shot CLI commands sharing one SQLite database
  (schema v9). There is no portal daemon, no HTTPS listener, and no user,
  session, or API-key model.
- The portal deletes objects only through applied GC proofs, but an agent
  cannot tell a GC delete from any other request.
- On the reference host the LocalAPI socket (`/var/run/tailscale/tailscaled.sock`)
  is world-writable, and a non-root process can call `WhoIs`; certificate
  issuance needs root or the tailnet operator user.

## Constraints

- Ride the host `tailscaled` through LocalAPI. No tsnet and no extra
  tailnet nodes (DESIGN §3).
- **Never disable the owner's tailnet HTTPS.** Its certificates serve the
  owner's remote-access setup. M2 tests may use the owner's tailnet,
  including fetching this node's certificate through LocalAPI, but must not
  turn HTTPS certificates off, change `tailscale serve` or Funnel
  configuration, or edit ACLs. The reference host has no serve or Funnel
  configuration; the portal defaults to port 8443, not 443. As of
  2026-10-28 `tailscaled` on the reference host holds no certificate, so
  the first live fetch issues a new one and publishes the host's tailnet
  name in Certificate Transparency logs; that step waits for the owner's
  go-ahead.
  Renewal and failure paths are tested against a fake LocalAPI with
  generated certificates, because a live certificate cannot be forced to
  expire. Certificate fetches need root (or the tailnet operator user), so
  the live test runs under `sudo`.
- WhoIs authenticates the network peer, not the process (DESIGN §3), so
  every internal operation also needs a portal-signed capability grant.
- Existing M1 drills and tests run agents on loopback. Loopback stays
  available only as an explicit insecure development mode, and even there
  grants are required; only the WhoIs node check is skipped.

## Decisions

1. **LocalAPI client.** A small HTTP/1.1 client over the Unix socket
   (`hyper` client connection, host `local-tailscaled.sock`) behind a
   `LocalApi` trait with three calls: `status` (own tailnet addresses and
   stable node id), `whois(addr)` (peer node and user), and `cert_pair`
   (certificate and key for a domain). Tests run the real client against a
   fake LocalAPI server on a temporary Unix socket. The socket path can be
   overridden with `DISTR_HNSW_TAILSCALE_SOCKET`. macOS LocalAPI transport
   is out of scope for M2; macOS hosts can be clients and test peers.
2. **Bind discipline.** `--bind tailnet:<port>` resolves the node's tailnet
   IPv4 address through `status`. An explicit address must be one of the
   node's tailnet addresses. Wildcards are always refused. Loopback needs
   `--insecure-loopback`, which health reports. A watcher polls `status`;
   if the tailnet address changes or disappears the daemon stops accepting
   and exits with a distinct status so its supervisor restarts it, and it
   never rebinds to a non-tailnet address. While `tailscaled` is not ready
   at startup the daemon retries with backoff instead of falling back.
3. **Capability grants.** The portal holds an Ed25519 signing key, stored
   encrypted under the master key (DESIGN §10). A grant v1 is a canonical
   binary record, base64url in an `Authorization: DistrGrant …` header,
   carrying: version, signing key id, grant epoch, agent id, agent
   incarnation, operation (`put`, `get`, `delete`, `inventory`, `health`),
   object kind and hash (or the inventory kind), the GC proof id for
   `delete`, issue time, expiry (at most five minutes), and a nonce. An
   agent accepts a grant only if the signature verifies under a key in its
   trusted key set, the epoch is current, the agent id and incarnation are
   its own, the operation and object match the request, and the grant has
   not expired (60 s clock-skew allowance). `delete` grants are issued only
   while applying a GC proof and name it. Replaying an unexpired grant can
   only repeat the same idempotent operation on the same object.
4. **Grant epoch.** One cluster-wide epoch, stored by the portal and in each
   agent's trusted key set. Raising it invalidates every outstanding grant,
   which is the revocation path. Placement epochs for partitions arrive
   with the vector plane (M4) and reuse the same check.
5. **Join.** The operator starts an agent with a single-use join token
   generated by `portal agent token`. The agent stores only the token's
   BLAKE3 hash and serves nothing but `POST /v1/join` until joined. `portal
   agent join` calls that endpoint with the token and a key-set document
   signed by the portal. The agent checks the token, burns it, pins the
   caller's WhoIs node id as the portal node, and stores the key set on its
   volume. The portal resolves the agent's WhoIs node id from the
   connection and records `agent_id → node id`. Tokens are single-use on
   both sides.
6. **Key rotation.** The key set lists active and retiring verification
   keys. Rotation adds a new key, distributes the set, signs with the new
   key, and later retires the old one. Revocation removes a key and raises
   the epoch. Agents accept a key-set update only if it is signed by a key
   they already trust and its version is newer.
7. **Portal daemon.** `distr-hnsw portal serve` binds HTTPS on the tailnet
   address only, with certificates from LocalAPI hot-reloaded through a
   rustls certificate resolver and renewed when a third of their lifetime
   remains. With no valid certificate it serves nothing; there is no
   plaintext fallback. Every connection is resolved with WhoIs on the socket
   address; identity headers (`Tailscale-User-Login` and similar) are
   ignored and logged.
8. **Users, sessions, API keys, audit.** Schema v11 (v10 went to grants)
   adds users, `identities (provider, external_id) → user_id` (provider
   `tailscale`, keyed by login name, the name ACLs use), sessions (BLAKE3
   verifier of a 256-bit token, bound to the creating node and user,
   12-hour lifetime, 1-hour idle limit), API keys (`dhk_<id>_<secret>`,
   a BLAKE3 verifier of a 256-bit secret, collection scopes with `read`,
   `write`, or `admin`, optionally bound to one node), and an append-only
   audit log (triggers refuse `UPDATE` and `DELETE`) of authentication
   events and state-changing requests. Cookies are `__Host-` prefixed,
   `Secure`, `HttpOnly`, `SameSite=Strict`; a state-changing request on a
   session needs the session's CSRF token and a same-origin `Origin` or
   `Sec-Fetch-Site` when the browser sends them. Single-user v1,
   multi-user-ready schema (DESIGN §9).

## Progress

- **Work package 1 — done 2026-10-28.** `crates/distr-hnsw/src/tailscale.rs`
  holds the LocalAPI client (`status`, `whois`) and bind discipline
  (`--bind tailnet:<port>`, `--insecure-loopback`, startup wait, address
  watcher with exit status 75). Agent health reports `bind_mode`. Until
  work packages 2 and 3 land, an agent resolves a tailnet bind but refuses
  to serve on it, because its routes are still unauthenticated. Tests:
  `tests/tailscale_localapi.rs` (fake LocalAPI). Every drill and process
  test passes `--insecure-loopback`.
- **Work packages 2 and 3 — done 2026-10-28.**
  - `grant.rs`: grant v1 and key-set v1, canonical binary with domain
    separation and Ed25519 signatures; verification names each rejection.
    A rotated key set carries signatures from the old and new keys.
  - `trust.rs`: the agent's trust state on its volume (join-token hash,
    then the signed key set and the pinned portal node), replaced durably.
  - `agent.rs`: `POST /v1/join`, `PUT /v1/trust`, and a grant check on
    every other route; on a tailnet address the caller must be the pinned
    portal node (WhoIs). A grant whose epoch is newer, or whose key is
    unknown, gets 409 with `x-distr-key-set-outdated`. The tailnet-serve
    guard from work package 1 is gone.
  - `access.rs` and schema v10: signing keys sealed under the master key
    (created at `portal init`), grant epoch and key-set version, joined
    agents, join tokens (stored as BLAKE3, 24-hour lifetime, single use).
  - `agent_client.rs`: `AgentClient` signs a grant for every portal request
    (health, inventory, get, put, and delete with its GC proof), pushes the
    key set on 409 and retries once; `join_agent` handles a lost join
    reply by confirming with a granted health check. All agent calls in
    the portal, recovery, reconcile, lifecycle, and backup code use it.
  - CLI: `portal agent token|join`, `portal key show-signing|rotate-signing|
    retire-signing [--revoke]`, `--master-key` on every command that
    contacts agents, and `--join-token-file` / `DISTR_HNSW_JOIN_TOKEN` on
    `agent`.
  - Tests: `tests/agent_authorization.rs` (every route against missing,
    malformed, altered, expired, wrong-agent, wrong-operation,
    wrong-object, stale-epoch, newer-epoch, and unknown-key grants; deletes
    without a proof; single-use tokens; rotation and revocation) and
    `tests/tailscale_localapi.rs` (a tailnet-bound agent process serves
    only its pinned portal node and ignores forged identity headers).
  - `portal agent request` sends one granted health, inventory, get, or put
    request and prints the status, for drills and diagnosis (no delete).
  - `agent --reset-trust` forgets the trusted portal and arms a new token,
    for a portal rebuilt without its signing keys (a lost database with no
    snapshot). It is a local operator action on the agent's host.
  - An agent that trusts another portal refuses its key-set push, and the
    caller sees that refusal (403 `key_set_untrusted`).
  - `scripts/tailnet-authorization-drill.sh` checks the same refusals on
    the real tailnet from another node; it passed from `25e31be`, and the
    M1 drills passed again with grants
    ([m2-authorization-drill.md](m2-authorization-drill.md)).
  - Grants bind the agent id, not the volume incarnation: a superseded
    volume that returns accepts the newer key set, and the portal's
    incarnation check (M1) is what keeps it out.
  - Retiring a key without `--revoke` does not push the smaller key set:
    agents keep accepting the retired key until their next key-set update.
    Use `--revoke` when a key may be compromised.

- **Work packages 4 to 6 — implemented 2026-10-28; live certificate
  evidence pending.**
  - `portal_server.rs`: `portal serve` resolves its bind like an agent but
    never accepts loopback; it serves only HTTPS and only after obtaining a
    certificate. Every connection is resolved with WhoIs before the TLS
    handshake, and an address WhoIs cannot name is dropped and audited.
    `Tailscale-*`, `X-Forwarded-*`, `Forwarded`, and similar identity
    headers are stripped, logged, and audited. Routes: `GET /api/whoami`,
    `POST|DELETE /api/session`, `GET|POST /api/keys`,
    `DELETE /api/keys/{id}`, `GET /api/audit`, `POST /api/files`,
    `GET|DELETE /api/files/{id}`. File operations run one at a time on a
    worker thread that owns the portal; uploads stream to a spool beside
    the database. Idempotency keys are namespaced per principal.
    Connections have a 10 s header-read timeout and a 10-minute lifetime
    (WhoIs is resolved again on reconnect) and are capped per address and
    in total; uploads and downloads are capped and check spool space.
  - `auth.rs` and `metadata/identity.rs` (schema v11): decision 8. Login is
    `POST /api/session` from a node whose WhoIs login belongs to a user;
    tagged nodes cannot sign in and use API keys, and the portal's own node
    cannot sign in unless `--allow-portal-node-sign-in` is set. Sign-ins
    are rate-limited per node. A cookie presented from another node or
    user is revoked. A login that presents a live cookie revokes it
    (rotation); disabling a user revokes all sessions and keys. An API key
    names its node (DESIGN §9: node and key are both checked) unless it is
    explicitly created for any node.
  - Audit: a state change is recorded `allowed` before it runs (and does
    not run if that write fails), then `completed` or `failed`; file
    changes are recorded by the worker, so a client that hangs up cannot
    skip them. Refusal and observation records are rate-limited per peer
    and their peer-supplied fields are length-capped.
  - An independent security review (2026-10-28) found the hang-up audit
    gap, unbounded audit growth, sign-in from the portal node, unbound API
    keys, missing connection limits, unbounded spooling, and unaudited
    refusals; all are fixed and covered by tests.
  - `tls.rs`: certificates from LocalAPI `cert/<domain>?type=pair` behind a
    rustls resolver; renewal starts when a third of the lifetime remains
    and retries with backoff; the resolver serves only a currently valid
    certificate, so an expired one refuses handshakes, never plaintext.
  - CLI: `portal serve`, `portal user add|list|disable`,
    `portal api-key create|list|revoke`, `portal audit`.
  - Tests: `tests/portal_server.rs` against the fake LocalAPI (now in
    `tests/common`), with loopback aliases standing in for tailnet nodes:
    WhoIs-only identity and forged headers, the session and CSRF matrix
    (cross-node cookie, rotation, logout, expiry, idle, disable), API-key
    scopes and verifiers, certificate renewal, hot reload, expiry with no
    plaintext answer, and recovery, and the bind refusals and exit 75 on
    an address change.

## Work packages

| # | Package | Proves |
|---|---|---|
| 1 | LocalAPI client, fake LocalAPI, bind discipline and address watcher for agents | bind criterion |
| 2 | Signing key, grant v1, agent verification on every route; portal attaches grants; `delete` only from GC apply | grant criterion; agent DELETE and inventory closed first |
| 3 | Join tokens, key-set document, portal and agent pinning, rotation and revocation | join and rotation criterion |
| 4 | Portal daemon: tailnet bind, WhoIs identity, header-forgery rejection | identity criterion |
| 5 | Schema v11: users, identities, sessions, CSRF, API keys, audit log | session, CSRF, and API-key criteria |
| 6 | Certificates: LocalAPI fetch, renewal, hot reload, failure behavior (fake LocalAPI) | certificate criterion, except live evidence |
| 7 | Adversarial drills: unauthorized tailnet node, forged headers, replayed and stale grants, rotation and node-join drills; ACL and certificate-transparency documentation | exit gate |

Packages 1 to 3 change the blob plane's internal API and run first: they
close the open `DELETE` and inventory surface on agents. The M1 drills move
to grants in the same packages so they keep passing.

## Verification

- Unit and property tests for grant encoding, signature, expiry, and every
  rejection reason; a request-level authorization matrix (every route ×
  missing, expired, altered, wrong-operation, wrong-object, wrong-agent,
  stale-epoch, and valid grants) for agents and later for portal routes.
- Process tests with the fake LocalAPI: address change, `tailscaled`
  unavailable at start, certificate expiry and renewal failure.
- Real tailnet: an agent bound to the reference host's tailnet address
  must refuse requests from the development laptop (no grant, and a node
  that is not the pinned portal), and the portal must serve HTTPS with the
  node's tailnet certificate to a client on the laptop. Neither changes
  tailnet settings.
- M1 drills (restore, lifecycle matrix, power loss, capacity) re-run with
  grants enabled.

## Open items

- **Live certificate evidence** comes from the owner's tailnet (approved
  2026-10-28): issuance through LocalAPI, TLS serving with that
  certificate, and a client on the development laptop validating it.
  Renewal and failure behavior come from the fake LocalAPI. Because the
  reference host has no cached certificate, the fetch is a new issuance
  (a public CT log entry) and waits for the owner's confirmation.
- **ACL policy** is documented, not applied: the owner applies it to their
  own tailnet.
